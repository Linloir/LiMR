# 性能测量

日期：2026-10-12。环境为 Intel Core i7-13700、WSL2/Linux、Node 20.19.5、Chromium 156.0.8078.4。React 19 production build；对照为 react-markdown 10.1.0 + remark-gfm 4.0.1。

以下是本机固定夹具的实测值。浏览器静态渲染与基线接近；流式追加减少了明显的重复工作。几个百分点的静态差异不应解读为所有设备和内容上的胜负；本轮 Node 长文 SSR 波动较大，也没有显示出性能优势。

## 浏览器

双方都渲染同一份 GFM：标题、强调、链接、行内代码、列表和表格，使用相同排版样式。LiMR 开启正常交互和原文映射能力。这里只比较正文，不把目录、侧栏等基线不具备的 UI 算进去。

每组运行三次、取中位数；每次用独立页面，先预热并等待字体，交替运行两个渲染器，避免上一组 DOM/内存影响下一组。计时范围是同步 React 提交和一次强制布局；不计网络下载、异步重资源加载、帧间空闲时间及后续观察器工作。

| 场景 | LiMR | react-markdown |
| --- | ---: | ---: |
| 87,381 字符，200 节，首次挂载 | 126.1 ms | 134.0 ms |
| 877,782 字符，2,000 节，首次挂载 | 1,345.4 ms | 1,437.6 ms |
| 34,860 字符，256 字符/次，138 次提交，累计同步时间 | 306.1 ms | 1,864.1 ms |
| 同一流式场景，单次提交 P95 | 2.9 ms | 23.7 ms |

本次流式累计同步时间约为基线的 **1/6.1**。末次提交执行最终完整解析，也包含在统计内。三轮 LiMR 流式单次最大值为 31.1–31.8 ms，不能将 P95 解读为每一帧都小于 16 ms。

长文夹具最终 DOM 元素数：LiMR 40,002，基线 36,001。差异主要来自表格滚动容器、代码文本映射及一个选区绘制层；普通段落、标题和文本不再依赖额外包裹层。未使用虚拟化，浏览器仍能搜索、选择和打印整个文档。

原始样本：[browser.json](../benchmarks/results/browser.json)。

## 持续拖选

真实鼠标持续按下并移动 90 次，结束前统计更新和绘制，不能用松手后的单次更新通过检查。每组使用三个独立页面，等待字体和代码着色后开始；下表展示按手势总时长排序的中间样本。绘制延迟是 `selectionchange` 到覆盖层 DOM 变更的间隔，帧间隔由 rAF 采样，均不等同于硬件输入到屏幕呈现的延迟。

| 场景 | 原生选区变化 | 拖动中的更新 / 绘制 | 绘制延迟 P95 | 帧间隔 P95 | 长任务 |
| --- | ---: | ---: | ---: | ---: | ---: |
| LiMR：877,782 字符，8,000 区块 | 91 | 75 / 75 | 25.2 ms | 16.8 ms | 0 |
| react-markdown：同一篇长文 | 91 | 无自定义覆盖层 | 不适用 | 16.7 ms | 0 |
| LiMR：1,000 行 Shiki 着色代码 | 51 | 47 / 47 | 19.3 ms | 16.8 ms | 0 |

三轮长文的绘制延迟 P95 为 25.2–28.5 ms，代码为 18.9–19.4 ms。一次绘制只保留视口内片段；这两个手势结束前分别有 11、12 个绘制矩形。浏览器回归还会全选全文并滚动到中间，要求可见绘制跟随滚动且矩形数少于 250。

同一自动化长文手势在 LiMR 中耗时 3.23 秒，基线为 1.52 秒；基线没有原文映射和自定义覆盖层，不能用接近的 rAF 间隔宣称两者输入处理成本相同。保留全部样本以便继续比较，见 [selection.json](../benchmarks/results/selection.json)。

回归预算：更新及绘制次数均超过原生变化的 60%，绘制延迟与帧间隔 P95 小于 40 ms，拖动期间没有超过 100 ms 的任务。测试使用单 worker，避免并发浏览器争抢资源扭曲结果。该预算是当前夹具的回归门槛，不是任意设备的性能保证。

## Node / SSR

core 对照为同版本 mdast-util-from-markdown + GFM。core 除解析外还生成标题、脚注、角注、区块和原文元信息。SSR 对照使用等价 GFM 功能；没有把未加载的代码高亮或公式冷启动算成渲染优势。

| 场景 | LiMR | 对照 |
| --- | ---: | ---: |
| 87,381 字符，核心处理 | 109.32 ms | 101.78 ms |
| 877,782 字符，核心处理 | 2,702.76 ms | 2,864.73 ms |
| 87,381 字符，SSR | 123.85 ms | 135.80 ms |
| 877,782 字符，SSR | 5,508.29 ms | 2,720.70 ms |
| 34,860 字符，137 次核心追加及收尾，累计 | 164.04 ms | 2,673.74 ms |

核心追加对照每次重新解析整个前缀。不同组分别预热，GC 和 JIT 会影响数值，因此不能把“核心处理”和“SSR”两行相减当作精确的 React 渲染成本。本轮长文 SSR 的 LiMR 样本范围为 2.64–9.10 秒，对照为 2.70–5.03 秒；中位数明显较慢，波动原因未归因，不据此承诺长文 SSR 与基线相当。原始区间：[node.json](../benchmarks/results/node.json)。

## 实现要点和边界

- 追加时回退到末尾尚未稳定的顶层区块。先前的 Markdown 定义作为解析环境；新定义影响前文时完整校正；生成结束时完整解析。
- 源文本从不预处理改写，坐标是原始 UTF-16 偏移。普通文本在真正选择时才建立 DOM 文本节点到源码的映射；装饰和自定义布局按需采用显式绑定。
- 区块和未变化的目录保持引用稳定；交互、布局与文档分开更新。滚动不会触发重新解析。
- 选区跟踪按 rAF 合并事件，取消会被持续拖动反复重置的 debounce。语法扩展仅检查边界祖先；绘制按可见区块二分定位、缓存文本映射与字体测量，复用矩形元素。绘制层自身也限制为视口高度，减少超长页面上的布局和命中测试工作。
- 代码接近视口时加载所需语言/主题；流式代码暂停后高亮。公式和视频分别按需加载或点击加载。
- 角注的缓存按阅读器隔离。浏览器测试覆盖了预览切换展开时复用同一请求、再次打开命中缓存、数据变更后重新请求；默认渲染没有第三方 CDN 请求。

尾部若是非常长的单个代码块、列表或未闭合标签，重新解析该区块的成本仍会增长。全文 transform、修改中间内容、引用定义变化和收尾都会触发完整解析。这不是任意语法、任意编辑模式下的常数时间增量解析器。

这里的性能数据没有覆盖大型公式集、Shiki 冷启动、密集外部注释、第三方插件、完整 Reader 布局或真实移动设备。相关功能另有交互验证，但不能从这些 GFM 数据推导出它们的性能承诺。

## 复现

在仓库中运行，测量时不要并行运行构建或其他基准：

```sh
NODE_ENV=production pnpm bench
pnpm exec vite build
pnpm exec vite preview --host 127.0.0.1 --port 4174
# 另一个终端：
pnpm bench:browser
pnpm bench:selection
# 浏览器交互与持续拖选回归：
pnpm test:browser
```

脚本及夹具位于 `benchmarks/`、`playground/benchmark.tsx` 和 `playground/selection-benchmark.tsx`；结果写入 `benchmarks/results/`。
