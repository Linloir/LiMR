# KP 算法性能报告

[文档目录](README.md) · [English](../en/knuth-plass-performance.md)

本轮测试日期 **2026-10-14 (Asia/Shanghai)**. LiMR **1.0.1**, react-markdown **10.1.0**, Markstream React **2.0.19**, React/React DOM **19.3.0**, Node **v20.19.5**, Chromium **156.0.8078.4**. 13th Gen Intel(R) Core(TM) i7-13700; 24 逻辑核; 31.2 GiB; linux 6.18.40.1-microsoft-standard-WSL2.

KP 是 `typography="knuth-plass"` 的可选段落排版模式。本报告将纯求解器、浏览器排版与交互正确性分开；同时测量当前 standard、CSS justify 和 KP 三种排版模式。

## 算法与执行路径

实现使用 box/glue/penalty、四个松紧等级、TeX 整数 badness、相邻行和连字符罚分，通过活动节点寻找最小 demerits 路径。依次尝试 pretolerance、tolerance 和 emergency；默认阈值 100/200、emergencyStretch=16px。不可拆分的超宽对象保留可见。`prepareKnuthPlass` 缓存宽度、伸缩前缀和及断点辅助数据；重新给定行宽仍然求解，不是直接返回缓存答案。

浏览器层额外执行 Unicode 换行、Knuth–Liang en-US 断词、字体测量、行 DOM 与词间距写入、选区和高亮布局。段落接近视口时排队，读写分批；已有排版节点在滚动时保留。调度器在每个任务后检查约 6ms 预算，并不是可以中断单个长段落的硬限制。活动列表大小受输入、行宽、松紧度与各遍尝试影响，本轮规模曲线不构成最坏复杂度证明。

## 结论与使用边界

本轮 10,000 词合成段落的准备+求解中位数为 **7.479ms**，复用准备后的求解为 **6.721ms**。完整论文桌面滚动的合并 P95 为 standard **17.00ms**、KP **19.70ms**；KP 的 DOM 和主线程成本更高，宽度变化的额外耗时见上表。

算法微基准说明已测输入规模和路径的成本；实际可感知延迟还取决于字体、段落数量、DOM 和浏览器调度。KP 的长段落求解和宽度变化可能产生额外工作，不能由缓存滚动的结果推导出免费排版。需要最少排版工作时可使用默认 standard；需要段落级优化时评估 KP 的实际内容、窄列和设备表现。浏览器字形测量与 TeX PDF 不保证逐像素一致。本轮未覆盖所有语言断词词典、病态负宽度输入、任意 looseness 或物理低端手机，也未与原生 TeX 的运行速度做跨语言比较。
